# BANNED_BY API

`GET /api/v1/masternodes/ban-attribution?proTxHash=<64 hex>&banHeight=<height>` is a public, no-store, rate-limited lookup for one identity and one claimed ban block. `blockHash=<64 hex>` optionally pins the canonical hash; hashes are normalized to lowercase. Heights are integers from 1 through 2147483647. Missing, repeated, malformed or unexpected query parameters return 400. Internal failures return a sanitized 500, never a fabricated unknown response.

The response has `code: BANNED_BY`, the requested identity/height, `generatedAt`, collector status, attribution-enabled flag and confirmed collection coverage. `status: verified` has a single `chain_verified_penalty` proof: block/parent hashes, block time, attribution check time, commitment transaction, quorum type/base, pinned v23 scoring rule, invalid membership, exact before/after penalties and ban heights, nominal amount and applied delta. Q400_60 is type 2; Q60/41 is type 7. Other quorum types retain their numeric identity.

Evidence requires a fresh ready collector, enabled attribution, and the requested block inside its confirmed collected prefix. A partial prefix may contain a verified ban, but `caughtUp: false` stays visible. The lookup replays the stored full parent/block state pair in commitment order and compares every stored application to the result. Only the commitment with `causedBan: true` for this identity is selected; earlier penalties in the same block do not become ban causes. Incomplete context, malformed snapshots, registry changes or mismatches suppress the proof. The database must already contain collector-validated membership; this endpoint does not issue RPCs or reconstruct historical state on demand.

`status: unknown` always has `proof: null`. Reasons distinguish disabled/collecting/stale/unavailable collector, disabled attribution, before/after coverage, missing canonical block, hash mismatch, pending/unavailable/unsupported/inconsistent/not-applicable scoring, no attributed ban for this identity, ambiguity, and a read invalidated by collection/reorg/freshness changes. Unknown does not establish that a ban or commitment was absent. A request is about a historical identity/block event, not the node's current ban state.

`observerCount` counts distinct reporters with the exact block hash/height, quorum type/base and member identity, among unexpired ban/penalty/member observations whose times are not in the future and passed the receipt check. It is separate unverified log evidence; duplicates or mismatched reports cannot add bans or supply a missing scoring cause. Verified scoring does not establish why DKG membership was invalid. No raw snapshots, service addresses, keys or log samples are returned.

Each request reads one indexed canonical block and exact observation anchors, with 10-second database query limits. Stored-state validation is bounded to 20,000 identities per snapshot and 64 commitments per block; excessive/malformed context remains unknown. The final collector generation/checkpoint check retracts evidence after concurrent rollback/ABA or freshness expiry. No cache or stale evidence fallback is used.

The Ban Detection page has a per-row **Ban evidence** button. It selects an identity and historical height in a shareable `/ban-detection?node=<proTxHash>&ban=<height>` URL. The panel separates ban anchors, verified scoring, DKG commitment and unverified observations. An unselected or invalid URL does not trigger an attribution query. A failed refresh, expired collector/response snapshot or mismatched identity retracts the causal display. A historical ban never establishes the node's current ban state.

Observation details load only when opened, 20 event groups per page with manual pagination. They request the exact identity, block height/hash, quorum type/base through `/api/v1/network-noise/pose-events`. The view shows retained events in the last 8760 hours; missing rows do not establish that no report existed. Counts within groups may overlap and are never summed into a network-wide observer count. These reports remain `log_observed` / `unverified`, including conflicting scores; the view does not render raw log samples.

Collectors/attribution remain disabled by default; the endpoint and UI enable no collector/probe/backfill, and change no production configuration or consensus rule.
